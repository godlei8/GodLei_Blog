GitHub Actions 别再复制粘贴 YAML 了，可复用工作流比你想的更值钱

更新于 2026/5/17 约 8 分钟阅读 2,341 字
DevOps GitHub Actions CI/CD YAML
复用只是表面，统一才是底层收益。聊聊 reusable workflows 真正值钱的地方。

很多团队的 CI 配置有一个很典型的成长轨迹：一开始只有一个 workflow，后来项目多了，分支策略多了，部署环境多了，于是 YAML 文件越堆越多。最开始是复制一份稍微改改，后面就变成"每个仓库看起来都差不多，但又总有一点不一样"。

这时候最可怕的不是文件多，而是维护开始失控。GitHub 官方把 reusable workflows 设计出来，本质上就是在解决这个问题：通过 workflow_call 把一个工作流变成可复用单元，再由其他 workflow 直接调用。

它最核心的价值，不是复用，而是统一

复用只是表面，统一才是底层收益。当你把构建、测试、部署的逻辑收敛到一处，所有调用方自动获得同一套行为——升级一次，全线生效。

把"每个仓库各写一份"变成"一处定义、处处调用"，维护成本是从 O(n) 降到 O(1) 的差别。

一个最小可调用的工作流

定义方只需要声明 workflow_call 触发器，并暴露需要的 inputs 与 secrets：

YAML 
# .github/workflows/reusable-build.yml
on:
  workflow_call:
    inputs:
      node-version:
        type: string
        default: "20"
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm run build

它和 action、composite action 不一样

这是最容易混淆的地方。三者的边界可以用一张表说清：

能力Reusable WorkflowComposite Action
能定义 job✅ 可以❌ 只是 step 集合
能指定 runner✅ 可以❌ 跟随调用方
能用 matrix✅ 可以❌ 不行
调用层级workflow 级step 级

哪些场景特别适合先改

不必一次性全量迁移，优先挑这几类：

  • 多个仓库共用同一套构建/部署流程
  • 安全扫描、镜像推送这类"全公司应该一致"的环节
  • 需要统一升级 runner、Node、JDK 版本的场景

我的结论

如果你的组织里有超过三个仓库在跑相似的 CI，reusable workflow 几乎一定能省下后续大量的维护精力。它真正值钱的地方，是把"散落的约定"变成"可执行的标准"。
